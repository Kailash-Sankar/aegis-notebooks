Plex on Aegis — end-to-end, two ways

A learning walkthrough of how a real source flows through the stack: a Plex Media Server (library + sessions) and a Plex TV app (high-volume playback telemetry). Same platform, two very different shapes.

The one idea that makes both work. Ingestion and the ingested (bronze) layer are generic — they are generated from a contract and don't care what the columns are. The prepared/aggregated layers are bespoke SQL you write (today) because "what is a session?" and "what is a good metric?" are business meaning, not schema. Everything below is an instance of that split.

The shared pipeline (used by both tabs)

connect (contract) → Sync now (pull, watermark) → gateway: validate + write raw + manifest
  → Redpanda ingest.chunks (claim check) → Inngest ingest-chunk-load
  → ClickHouse: ingested_*      (generic, engine deduped)
  → ClickHouse: prepared_* / aggregated_*   (bespoke SQL)
  → warehouse-refresh: hydrate 90d → Parquet
  → DuckDB hydrate_* views → notebook / agent / insights

Raw (RustFS) is the authority; everything after it is rebuildable. Delivered at-least-once; every write is idempotent (content-addressed raw + ReplacingMergeTree).

A · Plex Media Server

The server is a request/response API behind a token: it exposes your library (a dimension) and current playback sessions (a fact). Data changes slowly and is pulled incrementally by updated_at.

What we connect

DatasetKindGrainKeyEvent time
media_itemsdimension1 row / movie or episodecontent_idadded_at
playback_sessionsfact1 row / playback sessionsession_idstarted_at

Auth: Plex uses an X-Plex-Token header, which maps exactly to our header auth scheme. The contract stores only the reference; the secret lives in env or the gitignored credentials file.

The contracts

// sources/plex-server/contract.json  (media_items)
{
  "version": 1, "source": "plex-server", "dataset": "media_items",
  "baseUrl": "http://plex:32400",
  "auth": { "type": "header", "header": "x-plex-token", "secretRef": "PLEX_TOKEN" },
  "sync": { "mode": "incremental", "endpoint": "/library/all",
            "cursorField": "updated_at", "cursorParam": "updated_since", "pageSize": 200 },
  "load": { "target": "clickhouse", "layer": "ingested", "mode": "upsert",
            "dedupe": "latest_by_key", "key": ["content_id"] },
  "columns": {
    "content_id":  { "type": "UInt64" },
    "title":       { "type": "String" },
    "kind":        { "type": "LowCardinality(String)" },
    "duration_ms": { "type": "UInt64" },
    "added_at":    { "type": "DateTime64(3, 'UTC')", "eventTime": true },
    "updated_at":  { "type": "DateTime64(3, 'UTC')" }
  }
}
// sources/plex-server/contract.json  (playback_sessions) — same shape, key = session_id,
// eventTime = started_at, plus content_id / device_id / user_id / mode / bitrate.

End-to-end flow

The data model (star)

What is automatic vs. what you write

Automatic generic

  • Both ingested_* tables (contract → DDL)
  • Incremental sync + watermarks
  • Dedupe by session_id / content_id
  • Drift detection + additive columns
  • Raw authority + manifests

Authored (today: SQL) bespoke

  • prepared_media_items (dimension)
  • prepared_playback_sessions (fact + measures)
  • Which aggregates matter, and their grain
  • Insight rules ("transcode rate", "top library")

Example transforms

-- prepared: add measures to the fact (full, idempotent rebuild)
SELECT tenant_id, workspace_id, session_id, content_id, device_id, user_id,
       mode, bitrate_kbps, started_at,
       ifNull(ended_at, now()) AS ended_at,
       dateDiff('minute', started_at, ifNull(ended_at, now())) AS minutes,
       _version
FROM   ingested_playback_sessions FINAL;

-- aggregated: one row per day per content
SELECT tenant_id, workspace_id, toDate(started_at) AS day, content_id,
       count() AS sessions, sum(minutes) AS watch_minutes,
       avg(mode = 'transcode') AS transcode_rate
FROM   prepared_playback_sessions
GROUP  BY tenant_id, workspace_id, day, content_id;
Concepts to take away: dimension vs fact · grain · star schema · upsert + ReplacingMergeTree for rows that change (a session's ended_at is filled in later) · event-time partitioning (toYYYYMM(started_at)) so late corrections still sort correctly · idempotent full rebuilds.

B · Plex TV App (playback telemetry)

This is a different animal: a **high-volume event stream** from the client, not a slowly-changing API. Each interaction — play, pause, seek, rebuffer, stop, error — is a row. Events are immutable (they don't get updated), so there is no dedupe-by-key; correctness comes from a unique event_id and event-time ordering.

What we connect

DatasetKindGrainLoadEvent time
player_eventsraw events1 row / eventappend, no dedupeoccurred_at

Auth: the app authenticates with a per-device token → auth: { "type": "bearer", "secretRef": "PLEX_APP_TOKEN" }.

The contract

{
  "version": 1, "source": "plex-tv-app", "dataset": "player_events",
  "baseUrl": "https://telemetry.example.com",
  "auth": { "type": "bearer", "secretRef": "PLEX_APP_TOKEN" },
  "sync": { "mode": "incremental", "endpoint": "/v1/player-events",
            "cursorField": "occurred_at", "cursorParam": "since", "pageSize": 1000 },
  "load": { "target": "clickhouse", "layer": "ingested", "mode": "append",
            "dedupe": "none", "key": ["event_id"] },
  "columns": {
    "event_id":    { "type": "String" },
    "session_id":  { "type": "String" },
    "device_id":   { "type": "String", "pii": true },
    "user_id":     { "type": "String", "pii": true },
    "content_id":  { "type": "UInt64" },
    "event_type":  { "type": "LowCardinality(String)" },  // play|pause|seek|rebuffer|stop|error
    "occurred_at": { "type": "DateTime64(3, 'UTC')", "eventTime": true },
    "position_ms": { "type": "UInt32" },
    "buffered_ms": { "type": "UInt32" },
    "bitrate_kbps":{ "type": "UInt32" },
    "network":     { "type": "LowCardinality(String)" }
  }
}

End-to-end flow

Sessionisation — turning many events into one row

What is automatic vs. what you write

Automatic generic

  • ingested_player_events (append, no dedupe)
  • Content-addressed raw (duplicate batches are free)
  • Event-time partitioning + watermark
  • Idempotent re-loads
  • Drift detection / additive columns

Authored (today: SQL) bespoke

  • Sessionisation (raw events → session rows)
  • Which QoE metrics matter (startup, rebuffer, errors)
  • The conformed join with server sessions
  • Aggregate grain + insight rules

Example transforms

-- prepared: one row per session, with QoE measures (idempotent rebuild)
SELECT session_id, any(content_id) AS content_id, any(device_id) AS device_id,
       any(network) AS network,
       countIf(event_type = 'rebuffer') AS rebuffer_count,
       sumIf(buffered_ms, event_type = 'rebuffer') AS rebuffer_ms,
       countIf(event_type = 'error')    AS error_count,
       maxIf(position_ms, event_type = 'stop') AS end_position_ms
FROM   prepared_player_events
GROUP  BY session_id;

-- aggregated: QoE per day / device / network
SELECT toDate(occurred_at) AS day, device_id, network,
       quantile(0.5)(startup_ms)  AS startup_p50,
       quantile(0.95)(startup_ms) AS startup_p95,
       avg(rebuffer_ms / nullIf(play_time_ms, 0)) AS rebuffer_ratio,
       avg(error_count > 0) AS error_rate
FROM   prepared_client_sessions
GROUP  BY day, device_id, network;
Where this gets harder: telemetry is orders of magnitude higher volume than the server API, and events can be late/reordered. Sessionisation across a late boundary is the point where a simple batch rebuild stops being ideal and a streaming window (Flink/kafka Streams-style) earns its place. Our design already survives it — raw is the authority, so you can always re-run the model over the whole window.
Concepts to take away: event stream vs fact table · append-only vs upsert · ReplacingMergeTree vs plain MergeTree · sessionisation · event-time vs processing-time · late/out-of-order data · conformed joins across sources · QoE metrics (startup, rebuffer ratio, error rate).
