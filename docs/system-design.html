1. Overview

Aegis is a local-first analytical notebook: upload data (or ingest it from an external source), let an agent profile and map it, then open notebooks that chat over the data and build live dashboards and static reports. This document describes the analytics platform layered on top: a contract-driven batch pipeline that lands data in a real warehouse, materialises ingested/prepared/aggregated, and serves a window of it back to DuckDB for the notebooks.

The system is deliberately small but complete, and every heavyweight choice is paired with the industry equivalent it prepares you to compare against (Kafka, Airflow/Dagster, dbt, Prometheus, Confluent-style contracts).

2. Principles & authority model

The single most important rule: one authority per fact. There are four tiers, and each owns a different kind of truth. The system must be able to drop the warehouse and rebuild it entirely from raw + contracts — that is the “acid test” of the whole design.

Derived operating principles:

  • Accept vs. process. The gateway acknowledges acceptance, never completion.
  • Claim check. Queues carry small pointers/manifests, never bulk bytes (ADR 0008).
  • Contract-first. The agent writes a contract once; deterministic code executes it forever.
  • At-least-once + idempotent. Delivery is at-least-once; every write is idempotent.
  • Local-first. The query path (DuckDB) never depends on the network.

5. The pipeline, step by step

One chunk's journey, with the invariant each step protects:

  1. Generate — the mock source mutates SQLite: new events, point updates to current state, late-arriving rows (back-dated updated_at), and optional schema drift.
  2. Pull — the connector pages the source API with cursor + updated_since, handling rate limits (429 + Retry-After) and retrying transient errors with backoff. Invariant: only the first page applies the watermark; later pages advance by cursor, or the cursor tie-break is defeated.
  3. Land — the gateway validates against the contract, computes a content hash, writes JSONL to raw/<tenant>/<workspace>/<source>/<dataset>/<hash>.jsonl (content-addressed → free dedupe), and writes a chunk manifest. Invariant: raw is immutable; identical bytes are a no-op.
  4. Publish — the manifest (a claim check, not the payload) goes to ingest.chunks, keyed by workspace_id so a workspace's events stay ordered in one partition.
  5. Consume — the bridge reads fromBeginning (the group join can lag, and idempotency makes replay safe) and turns each manifest into an Inngest event.
  6. Load — the ingest-chunk-load workflow (durable, retried, serialised per workspace) reads raw by key, projects rows to declared columns + metadata, and inserts into ingested_<dataset>. Invariant: at-least-once → idempotent (ReplacingMergeTree + content address).
  7. Transform — prepared/aggregated are rebuilt with plain SQL (TRUNCATE + INSERT … SELECT), run as a second workflow step.
  8. Hydrate — a window of the warehouse (default 90 days) is exported to month-partition Parquet and exposed as hydrate_<table> DuckDB views.
  9. Query — the notebook (agent + UI) reads DuckDB; ClickHouse is never on the read path.

6. Source contracts — the standard

A contract is the declarative description of how to pull and shape one dataset. It is the only place that encodes source semantics; the connector and loader just execute it. The design goal: inference proposes → the agent decides → the schema validates.

Contract shape (abridged):

{
  "version": 1,
  "source": "twitch-mock",
  "dataset": "stream_events",
  "baseUrl": "http://mock-source:8099",
  "sync":  { "mode": "incremental", "endpoint": "/v1/stream_events",
             "cursorField": "updated_at", "cursorParam": "updated_since", "pageSize": 500 },
  "load":  { "target": "clickhouse", "layer": "ingested", "mode": "upsert",
             "dedupe": "latest_by_key", "key": ["event_id"] },
  "columns": {
    "event_id":   { "type": "String" },
    "channel_id": { "type": "UInt64" },
    "started_at": { "type": "DateTime64(3, 'UTC')" },
    "ended_at":   { "type": "Nullable(DateTime64(3, 'UTC'))" },
    "updated_at": { "type": "DateTime64(3, 'UTC')", "eventTime": true }
  },
  "quality":  { "notNull": ["event_id"], "unique": ["event_id"] },
  "physical": { "partitionBy": "toYYYYMM(started_at)", "orderBy": ["event_id"] }
}

The published JSON Schema is runner/src/sources/contract.schema.json; field roles (eventTime, pii, load.key, sync.cursorField) are the “semantic conventions.”

7. Warehouse & the layered model

ClickHouse is the analytical system of record. Every table carries tenant_id and workspace_id as the leading sort keys (shared database, isolation by predicate).

Ingested DDL (generated from the contract): upsert contracts use ReplacingMergeTree(_version) so the engine keeps the newest row per ORDER BY key; _version is derived from the event-time column so late arrivals still order correctly. Additive schema drift is applied with ALTER TABLE … ADD COLUMN IF NOT EXISTS.

8. Serving: hydration

Notebooks never query ClickHouse live. A hydration job exports a window to Parquet on local disk; DuckDB reads it.

What it does

  • Default rolling 90 days, overridable.
  • Month-partition Parquet under hydrate/<table>/.
  • Consistent as of a watermark T.
  • A manifest is the authority for what is cached.

Incremental rule

  • Closed months cached → skipped on refresh.
  • Open (current) month → re-exported.
  • New partitions → added; out-of-window → dropped.
  • Never blind-append: mutations rewrite old partitions.
Why this is the interesting part. Hydration is a cache-invalidation problem, not a copy. Closed partitions are assumed immutable; late data rewriting them is a documented limitation (the SCD / slowly-changing-dimension problem).

9. Scheduling & background insights

A small hand-rolled scheduler (definitions in code, lastRunAt in state.json, append-only runs.jsonl, in-process overlap guard) triggers periodic work. This teaches the primitives before adopting Dagster/Airflow.

JobIntervalDoes
warehouse-refreshhourlyRebuild prepared/aggregated per workspace, refresh the hydration window + views, record freshness.
insights15 minRecompute aggregated_insights: total watch today, top channel, peak-viewer anomalies (max > 2×avg).

Insights are deterministic SQL — facts, not prose. They are surfaced at GET /workspaces/:id/insights and in the notebook’s Insights tab.

10. Observability

Metrics are the backbone; logs are errors-only; traces are sampled. This keeps visibility without storage bloat.

Metric familyAnswers
aegis.freshness.secondsHow stale is the data? (the primary signal)
aegis.ingest.chunks|rows|dedupeIngestion throughput and dedupe rate
aegis.jobs.runs|durationAre scheduled jobs healthy?
aegis.http.requests|durationRunner API traffic/latency
aegis.queue.pendingPublished − consumed (local lag proxy)

Flow: runner SDK → OTel Collector (OTLP) → Prometheus endpoint on :8889 (or SigNoz via a collector exporter). The collector is the seam: swapping the backend is a config change, not app code.

11. Failure semantics & invariants

ConcernBehaviour
DeliveryAt-least-once. Offsets commit after the write; consumers must be idempotent.
DuplicatesContent-addressed raw → free dedupe; ReplacingMergeTree dedupes in the warehouse.
Transient errorsRetry with backoff, honouring Retry-After.
Terminal errorsClassified for the DLQ; a poison chunk never blocks the pipeline (head-of-line blocking avoided).
Slow consumersRead fromBeginning + concurrent partitions, so a group-join delay or one stuck partition can’t drop data.
Hanging control planeinngest.send is bounded by a timeout with an inline fallback; failed loads are logged, not fatal.
Schema driftAdditive changes auto-apply (ADD COLUMN IF NOT EXISTS); removals/type changes gate on review.
ConsistencyHydration is stamped “data as of T” for reproducibility.

16. Run & operate (appendix)

Bring up the stack

# registry + raw lake + transport + warehouse + control plane + source
docker compose up -d --build rustfs redpanda clickhouse inngest mock-source runner

# scrape metrics
curl -s localhost:8889/metrics | grep '^aegis_'

Ingest → warehouse → serve (operator flow)

WS=$(curl -s -X POST localhost:8787/workspaces -H 'content-type: application/json' \
       -d '{"name":"demo"}' | jq -r .id)

# 1) contract (or let the agent do it via discover_source / write_source_contract)
mkdir -p "workspaces/$WS/sources/twitch-mock"
# ... write workspaces/$WS/sources/twitch-mock/contract.json ...

# 2) pull (connector -> raw -> Redpanda -> Inngest -> ClickHouse ingested/prepared/aggregated)
curl -X POST "localhost:8787/workspaces/$WS/sources/twitch-mock/pull"

# 3) detect drift at any time
curl "localhost:8787/workspaces/$WS/sources/twitch-mock/check"

# 4) hydrate the DuckDB window, then inspect the warehouse views
curl -X POST "localhost:8787/workspaces/$WS/hydrate" -d '{"days":90}'
curl -X POST "localhost:8787/workspaces/$WS/query" \
  -H 'content-type: application/json' \
  -d '{"sql":"SELECT count(*) FROM hydrate_aggregated_stream_daily"}'

# 5) scheduled jobs + insights
curl localhost:8787/scheduler
curl -X POST localhost:8787/scheduler/run/warehouse-refresh
curl "localhost:8787/workspaces/$WS/insights"
